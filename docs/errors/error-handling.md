# Обработка ошибок и режимы отказа

Сейчас проект опирается на логи Unity (`Debug.LogError`) и guard-условия внутри систем.

Связанные документы: [Цикл выполнения](../flows/runtime-loop.md), [Конфигурация](../config/configuration.md), [Стратегия тестирования](../testing/testing-strategy.md).

## Текущие паттерны обработки ошибок
- Валидация в bootstrap:
  - отсутствие transform игрока отключает bootstrap-компонент.
  - отсутствие `Rigidbody2D` у игрока приводит к ошибке в логах.
- Guard-проверки в системах:
  - сущность пропускается при отсутствии обязательных компонентов/ссылок.
  - путь ввода пропускается, если недоступна `Camera.main`.
- Отложенное удаление:
  - удаление сущности выполняется во время flush мира, чтобы не мутировать коллекции при итерации.

## Известные слабые места
- Нет централизованной таксономии ошибок (warning vs hard-fail).
- Нет метрик/телеметрии по пропущенным входам и сущностям.
- Нет проверок, гарантирующих порядок регистрации систем и корректное wiring сцен.

## Рекомендуемые шаги
- Ввести легковесные диагностические счетчики в системах.
- Добавить startup self-check для проверки bootstrap и обязательных ссылок в активных сценах.
- Добавить play-mode тесты для сценариев `null`-камеры и отсутствующего `Rigidbody2D`.

Влияние архитектурных границ см. в [Обзор API](../api/overview.md), архитектурные ограничения — в [Обзор архитектуры](../architecture/overview.md).
